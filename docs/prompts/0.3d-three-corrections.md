## 1 — Evals run on Groq (amends D24d, rewrite ADR 0010's eval section)

You were right to flag the cost, and the cost is worse than the contention it
avoided. Publishing faithfulness and citation-accuracy numbers measured on a
model no user ever touches would make the eval page misleading, and the eval
page is a portfolio artefact.

- Published eval numbers run on **Groq**, the production path.
- The full 60-question run moves from **nightly to weekly**: ~300K tokens once a
  week instead of half the daily budget every day.
- The per-PR subset shrinks and becomes **path-filtered** — run it only when the
  change touches prompts, retrieval or `packages/core`.
- **Gemini keeps local iteration only**, where you care whether a prompt change
  moved the number, not what the number is.
- Every published run records provider, model and prompt version. `eval_runs`
  already has the columns; make sure the harness fills them.

This is a decision change, not an implementation task — 2.5 builds the harness.
Update ADR 0010 and note that it supersedes the earlier Gemini-for-evals line.

## 2 — Return the allowance from the `activity` kind (D25)

The web app shouldn't hold its own copy of 10/1 and 3/0; it will drift. The app
already calls `activity` once per session on load, so have that kind return the
caller's allowance and remaining counts instead of null. No new function, no new
privileged surface. Remove the duplicated constants from the web app and the
note from ADR 0011.

## 3 — Guard the race test

It commits to the real database and once needed hand repair. The cleanup block
helps, but the real fix is refusing to run in the wrong place: reuse the guard
the suite already has for service-role keys, and make the race test refuse to
start unless it's pointed at a local or CI database.

While you're there: derive the container name from `project_id` in
`config.toml` rather than hardcoding `supabase_db_litlens`, or fail with a
message that names the cause. Right now renaming the project breaks the test in
a way that won't be obvious.

## Tests

Point 2 needs tests: `activity` returns the right allowance for a signed-in user
and for an anonymous session, and the numbers match `private.daily_allowance`
rather than a constant written anywhere else. Mutation-test that last part —
hardcode a wrong number in the function and make sure a test fails.
